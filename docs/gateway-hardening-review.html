The findings that gated exposure are closed. All five criticals and all seven highs are fixed and verified against a running instance: the management plane authenticates and authorizes per action, tokens are revocable, the signing key is off the web tier, guardrail patterns are bounded, and the dashboard's XSS chain no longer reaches the admin credential.

The last five, and what closing them found

The long tail is done. Two of these turned up something that was not visible from reading the finding.

L4

Turning on the audit immediately failed the build

UnifiedGatewayV2.csproj · .github/workflows/ci.yml
Found
Enabling NuGetAudit surfaced six high-severity advisories on the first restore — one in System.Formats.Asn1 and five in System.Security.Cryptography.Xml.
Cause
They all arrived transitively through Microsoft.AspNetCore.DataProtection.Extensions — a package that had been dead weight since H7, when DataProtection was replaced by a KMS-backed signing key but the reference was left behind. Removing it cleared all six.
Now
Audit fails the build (not warns), a lock file is committed, and CI runs --locked-mode restore, CodeQL and gitleaks with full history. A weekly schedule catches advisories published after a merge.
M6

The scope claim now bites

Models/GatewayScopes.cs · Services/SecurityService.cs
Rules
* grants everything and admin implies invoke; nothing else is implied. A token with no scope at all is treated as invoke-only, so an old token cannot outrank a new one.
Verified
Same application, same signing key, three scopes: read → 401, invoke and admin → through to the backend. The universal endpoint requires the admin flag and admin scope, so an admin-minted token that was scoped down stays scoped down.
Also
An unrecognised scope is rejected at issuance with a 400 naming the valid values, rather than silently granting less than was asked for. That first surfaced as an unhandled 500 and was fixed.
M1

Every record now says who

Models/CallerContext.cs · Services/ModelRouter.cs
How
A CallerContext is built at the endpoint and threaded into the router explicitly rather than read from an ambient HttpContext — attribution that silently disappears outside a web request is worse than none.
Verified
A live invocation writes actor=ug_live_47a6, authType=AppApiKey, plus source IP and trace id. The actor is the key prefix, never the key. An STS-authenticated call records the token's jti instead.
Side effect
This is what made the traceId correlation claim in architecture.md true, rather than requiring the claim to be deleted.
L3

Errors reference, they do not describe

ModelRouter.cs · LocalModelService.cs · BedrockService.cs
Now
All four sites return a stable code and a correlation id; the exception is logged against that id. An AWS exception routinely carries the account id, the role ARN and a request id — that belongs in the log.
Kept
The local-model timeout message stays detailed, because it names configuration the operator can change (the timeout and the token budget) rather than infrastructure. That distinction is the rule, not an exception to it.
L1

The sign-off table now records failures too

architecture.md §3, §5
Corrected
The DataProtection and non-root-container claims are gone — the latter replaced by an explicit note that there is no container and the previous claim described an image that does not exist. Deleting it quietly would have been the same mistake in reverse.
Changed shape
The table previously listed only controls marked PASSED. It now carries eight open rows alongside the implemented ones, each citing implementing code rather than the file that mentions it. A sign-off document that only records successes is how gaps get formally accepted.

Added since the baseline

Capability that was not in the original review, and is now part of the security surface.

Okta authentication Simulated tenant with hard-coded users and AD groups, RS256 tokens with a JWKS endpoint, and group-to-IAM-role mapping. Forgery attempts including alg:none and group escalation all rejected.
Role separation, enforced Admin and developer roles evaluated per action by the IAM policy engine. A developer gets 403 on create, delete, billing, metrics and guardrail changes.
Billing and cost monitoring Per-application rate cards, cost frozen at write time so a re-price cannot restate a past invoice, and an admin-only page behind gateway:ReadBilling.
Telemetry in object storage The audit trail moved from local files to S3, partitioned by record date. It now outlives any single host, which is what an audit trail has to do.
Dev / prod parity One binary across environments; Gateway:Cloud:Provider is the only switch, and startup refuses a simulator provider outside Development.
Guardrail failure mode A scan that times out is reported as a violation rather than a pass, so an input the scanner could not finish reading is never cleared.

New risks the additions brought

These were not in the original 26. The first one matters most.

N1

In production the gateway does not verify identity itself

Services/Cloud/Aws/AwsProviders.cs — AwsIdentityProvider
What
AwsIdentityProvider reads an asserted principal ARN and checks only that it looks like an ARN. It performs no SigV4 verification and no OIDC validation; it assumes an ALB or API Gateway in front has already authenticated the caller.
Why it matters
If the gateway is ever reachable directly — a misconfigured security group, a health-check path, an internal caller bypassing the edge — anyone can assert any role ARN and be believed. That is the C1 hole again, in a different place. The dev and simulator paths do verify properly; production is the one that does not.
Fix
Either verify SigV4 in the gateway, or validate the Okta JWT directly in production the way the simulator path already does, and stop accepting a bare header assertion. Until then, treat direct network reachability as a critical misconfiguration and enforce it at the security group.
N2

The entire AWS provider path is unverified

Services/Cloud/Aws/AwsProviders.cs · ObjectStores.cs
What
Secrets Manager, KMS, S3, access control and identity all compile and follow the contracts their simulator counterparts were tested against, but no AWS account was available, so not one line of the production path has executed.
Why it matters
Test and Production are both configured for Aws. The first real run of that code will be the first time it has run at all.
Fix
Exercise it in a staging account before it fronts anything. Bootstrap alone touches KMS, Secrets Manager and S3, so a single successful start proves most of it.
N3

Production authorization depends on a hand-maintained secret

AwsAccessControlProvider — /gateway/access-policy
What
Management-plane authorization in AWS mode reads its policy document from a secret. If that secret is missing or malformed, every request is denied — correct, but it means a deleted secret is a full management-plane outage, and a hand-edited one is an unreviewed permission change.
Fix
Manage it as code with the rest of the IAM policies and deploy it through the same pipeline, so a permission change goes through review rather than a console edit.
N4

Buffered telemetry can be lost on an unclean stop

Services/Telemetry/S3AuditStore.cs
What
Records are batched and flushed every 30 seconds, on a full batch, before reads, and at shutdown. A failed flush retries. But a hard kill loses up to one interval of billing and audit records.
Why it matters
It understates an invoice silently, and a compliance trail with holes is a weaker claim than one without. This is the deliberate cost of S3 objects being immutable, not a defect — but it should be a known and accepted number, not a surprise.
Fix
Lower the interval to trade PUT cost for a narrower window, or write through a local spool that survives restart and drains to S3. Decide which, and record the decision.

Roadmap position

Against the phases in the original review.

Phase 0Complete

Every critical and high closed. This is what gated exposure beyond localhost, and it is done.

Phase 1Mostly

Operator identity through Okta, roles as IAM policies, and per-action authorization all work. Missing: per-app ownership, so an AppOwner still sees every application rather than only their own — and real-tenant sign-in uses the authorization-code flow rather than the simulator's password grant.

Phase 2Mostly

Revocation, key-generation binding, short TTLs and dual-source secrets are in. Missing: asymmetric signing via KMS — tokens are HMAC-signed with a key fetched from the secret store, which keeps the key off disk but still brings it into process memory.

Phase 3Partly

The audit trail is now durable and off-host. Still open: the application registry is a local file rather than a database, so the gateway remains single-node for writes; and nothing ships to a SIEM.

Phase 4Partly

Security headers, correct status codes and circuit breakers are done. Still open: per-app token budgets that actually refuse requests — the billing page reports spend but enforces nothing.

Phase 5Not started

No CI gates, no dependency or secret scanning, no penetration test, and the threat model still does not cover the management plane.

Scope and method

Each of the 26 original findings was re-checked against the working tree by reading the implementing code, not from memory. Behavioural claims — authorization outcomes, token revocation, rate limiting, status codes, storage layout — were confirmed against a running instance backed by the local AWS simulator. The AWS provider path was not executed; see N2.

The baseline was commit 133e4f5. Current state is the working tree on main, which is uncommitted. Line references drift as the code changes. This document supersedes the original review, which described the state before any remediation.
