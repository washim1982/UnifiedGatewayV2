Security architecture · Unified LLM Gateway

How the gateway is defended, and where it still leaks

Every control a request passes through, why each one is there, and the seventeen gaps a review of the design found. The four that let an outsider in — a management plane that trusted an asserted ARN, an admin-issuing Okta simulator, TLS that the installer never switched on, and unscoped break-glass tokens — are now fixed and covered by tests. Thirteen medium and low items remain.

Summary

The data plane was sound; the way into the management plane was not. Application keys are 256-bit and stored only as hashes, STS tokens are signed and short-lived, and both guardrails fail closed. But in AWS mode — the mode Production runs — any caller could name the admin role in a header and be treated as it, over plain HTTP, because the installer never created an HTTPS binding. That chain is now closed at every link.

What remains open are depth issues rather than open doors: rate limits a caller can sidestep, revocation that cannot target a single app, guardrail changes that are under-audited, routing that can send on-prem data to the cloud, backends reachable around the gateway, and an audit trail the gateway itself can delete.

System context and trust boundaries

Four caller types reach one IIS host. Behind it the gateway talks to AWS for identity, secrets, audit storage and models, and to on-prem inference servers over the local network.

Fixed

SL-01 · CRITICAL

AWS mode accepted any ARN string as an authenticated identity

Fixed
AwsIdentityProvider.cs · GatewayAuthentication.cs · Program.cs · aws-iam-authentication.md
Was
The handler passed whatever arrived in X-API-Key, Authorization or X-Simulator-Role to AwsIdentityProvider, which returned authenticated for any string beginning arn:aws: and used it as the principal. Role ARNs ship in the deployed config, so anyone who could reach the port held the management plane in Production and Test.
Fix
Identity in AWS mode is proven, not asserted.
  • Automation sends a SigV4-signed sts:GetCallerIdentity request in X-Gateway-Aws-Identity; its AWS secret never reaches the gateway.
  • Before contacting AWS the gateway requires a POST to an allow-listed STS host with no port, path or query; exactly Action=GetCallerIdentity&Version=2011-06-15; a signed X-Gateway-Server-Id equal to this gateway's (no replay from other services); and an X-Amz-Date within five minutes. Only signed headers are relayed; redirects are off.
  • STS verifies the signature. The answer is parsed with DTDs prohibited; the account must be allow-listed; assumed roles map to their role ARN; root and federated users are refused.
  • A bare ARN in any header gets 401. X-Simulator-Role is read only under a simulator. Off by default; when enabled, startup refuses loose scoping.
Proof
25 cases in SecurityLoopTests: asserted ARNs rejected in three headers; nine malformed requests refused without contacting AWS; wrong or unsigned server id, stale date, foreign account, STS rejection, root, federated user and DTD payload all refused; a valid request authenticates as the role and relays only signed headers. Not yet run against a real AWS account.
SL-02 · HIGH

Okta simulator with a hard-coded admin was on unless switched off

Fixed
appsettings.json · StartupValidator.cs · Program.cs · OktaAuthentication.cs
Was
The base config enabled the simulator, so Staging, UAT, DR or a mistyped environment name inherited a password-grant endpoint that issued trusted admin tokens for an account whose password is in source, plus an unauthenticated directory of users and role ARNs.
Fix
Defaults to off; the base file is now a template with <your-tenant> and <account-id> placeholders, and only Development switches the simulator on. Startup refuses it elsewhere and requires HTTPS, substituted issuer and metadata URLs and real role ARNs for the tenant — so an unconfigured environment refuses to boot. Endpoints are mapped, and the in-process key trusted, only in Development.
Proof
Refused in Test, Staging and Production; HTTP and placeholder issuers refused; placeholder role mappings refused; no shipped environment but Development runs it; Staging, which has no file, refuses to start.
Residual
The demo users are still compiled into OktaDirectory.cs. They are unreachable outside Development, but moving them to a Development-only file would keep them out of production binaries.
SL-03 · HIGH

Mandatory TLS was not enforced as deployed

Fixed
install.ps1 · HttpsEnforcementMiddleware.cs · Program.cs · StartupValidator.cs
Was
The installer created one HTTP binding on port 8080, so redirection had nowhere to go and HSTS never applied: keys, tokens and prompts travelled in clear. Test was treated as loopback and exempted from HTTPS and from app authentication, although it binds real AWS on a network host.
Fix
  • Installer: requires -CertificateThumbprint; checks the certificate exists with its private key, is unexpired, carries the server-auth EKU and covers -HostName; creates an HTTPS (SNI) binding, attaches the certificate and removes every HTTP binding. -AllowHttpRedirect and -DisableLegacyTls are opt-in; the script warns while TLS 1.0/1.1 remain enabled.
  • Application: /gateway, /api and /okta over HTTP get 403 HTTPS_REQUIRED — no redirect, because the key has already crossed the network and a followed redirect hides the misconfiguration. Browsers get a 308; HSTS lasts a year.
  • Validation: only Development may disable HTTPS or app authentication; Test now requires HTTPS; the role-name simulator is refused outside Development.
Proof
HTTP refused in Test and Staging; authentication cannot be disabled in Test; simulator refused outside Development; four API paths get 403 over HTTP; HTTPS and non-API paths pass. The installer passes the PowerShell parser but has not been run on an IIS host. Health probes must now use HTTPS.
SL-04 · HIGH

Admin STS tokens skipped scope, chose their own identity, and were minted unaudited

Fixed
GatewayAuthentication.cs · ApplicationRegistryService.cs · SecurityService.cs · StartupValidator.cs
Was
Minting an admin token with the master key wrote no audit record and no warning. On /api any admin token passed whatever its scope. Its principal was the first admin ARN — skipping IAM, explicit Deny included — or a role named by the token's self-chosen callerId; with no admin ARNs, break-glass mapped to the placeholder account 123456789012.
Fix
  • Scope: /api requires the admin scope.
  • Identity: master key and admin tokens act as the configured BreakGlassPrincipalArn; unset means refused, and startup requires it outside Development. The token's jti travels into the management audit record.
  • Audit and alerting: every issuance is recorded with token id, scope, lifetime, callerId and source IP (MintAdminStsToken, ExchangeApiKeyForStsToken); break-glass mints and uses log BREAK-GLASS: at Warning for the SIEM.
  • Lifetime and attribution: admin tokens capped at 15 minutes; callerId limited to a safe charset and recorded only as a label beside a server-derived identity.
Proof
read- and invoke-scoped admin tokens cannot manage; an admin token acts as the break-glass ARN whatever its callerId; so does the master key; break-glass fails closed without a principal and startup requires one; a mint is audited with token id and source IP; admin tokens are capped at 900 s; control characters and markup in callerId are rejected; data-plane attribution reads break-glass [label].

SL-05 · MEDIUM

Rate limits are keyed on a value the caller chooses

Program.cs:306 · Program.cs:483
What
The partition is a hash of whatever credential string is presented, before authentication, and the global floor uses the same function. A fresh random string per request is a fresh bucket, so unauthenticated calls to the token endpoint and /api are unlimited. No forwarded-headers handling: behind a balancer, IP fallback and audit SourceIp would record the balancer.
Fix
Partition unauthenticated and failed requests by client IP; switch to the credential only after authentication succeeds; add a per-IP failed-auth counter with backoff; configure UseForwardedHeaders before adding a balancer.
SL-06 · MEDIUM

Revocation cannot target one application or one token

SecurityService.cs:313 · ApplicationRegistryService.cs:326 · SigningKeyProvider.cs:72
What
Rotating an app key leaves its issued tokens valid for up to an hour. The jti denylist has no caller outside tests and is per node. Signing-key rotation reaches other nodes only after their 300 s cache.
Fix
A per-app key generation stamped into tokens and checked on validation; POST /api/tokens/revoke behind an IAM action with a persisted denylist; re-read the signing key on an unknown generation. The token id now in every issuance record is the handle a revocation would name.
SL-07 · MEDIUM

Guardrail weakening is not fully audited or persisted

DashboardEndpoints.cs:426 · GuardrailService.cs:30
What
The audit records only enabled and mode. Switching off PII, PCI, injection or output scanning reads enabled True → True; mode Redact → Redact. The change is in memory: it reverts on restart and applies only to one node.
Fix
Record the full before/after; alert when any detector turns off or the mode leaves Block/Redact; persist the policy, versioned, in Secrets Manager or Parameter Store.
SL-08 · MEDIUM

Guardrails are evadable pattern filters and skip the system prompt

GuardrailService.cs:40 · GuardrailService.cs:604
What
Run against the shipped patterns: ignore all previous instructions is caught; ignore the previous instructions and ignore previous instruction are not. 4111 1111 1111 1111 is caught; 4111.1111.1111.1111 is not. 123-45-6789 is caught; 123.45.6789 is not. The systemPrompt argument is never scanned, and Bedrock Guardrails is configured but unused.
Fix
Normalise (NFKC, strip zero-width, collapse separators in digit runs) before scanning; scan the system field; wire up Bedrock Guardrails or a classifier. Until then treat the guardrail as best-effort DLP.
SL-09 · MEDIUM

Routing fails open to the cloud

ModelRouter.cs:228 · ModelRouter.cs:301
What
An unknown provider or model goes to Bedrock; an app with a fallback model but no fallback provider falls back to the opposite host, so a local app falls back to the cloud. Neither field is validated.
Fix
Allow-list providers; make unknowns an error; require an explicit fallback provider; add a per-app OnPremOnly residency flag.
SL-10 · MEDIUM

On-prem model servers can be called around the gateway

appsettings.Production.json:43 · LocalModelService.cs:112
What
Ollama, LM Studio and llama.cpp have no authentication and are reached over plain HTTP on the network, so anyone who can route to them skips keys, guardrails, audit and billing.
Fix
Loopback or firewall to the gateway host only; a TLS reverse proxy with mTLS or a bearer secret in front.
SL-11 · MEDIUM

The audit trail can be erased by the principal it audits

S3AuditStore.cs:256 · AuditFlushService.cs:79
What
The gateway prunes by deleting S3 objects, so its role can delete its own history. Records wait in memory up to 30 s; failed flushes re-queue without bound; objects are not chained.
Fix
S3 Object Lock (compliance mode) with lifecycle retention; drop s3:DeleteObject from the role; bound the buffer; ship to the SIEM — where the new BREAK-GLASS: warnings should alert.
SL-12 · MEDIUM

Disabling access control passes startup validation

GatewayAuthentication.cs:320 · StartupValidator.cs:115
What
With AccessControl:Enabled: false every authenticated principal is authorized; the validator refuses this only when no admin ARN is listed, so one ARN plus a disabled engine starts, and every Okta Developer is an admin. (The placeholder-account half was fixed under SL-04.)
Fix
Refuse Enabled: false outside Development outright.

Key handling256-bit CSPRNG keys, stored only as SHA-256, compared in constant time, shown once.
Token validation orderSignature first, then generation, expiry and denylist; nothing parsed from an unverified payload.

Proven identitiesOutside Development every accepted credential is a cryptographic proof: Okta RS256, the gateway's HMAC, a constant-time key compare, or AWS STS.

DashboardEvery server value escaped, no inline handlers, script-src 'self', token in sessionStorage.
